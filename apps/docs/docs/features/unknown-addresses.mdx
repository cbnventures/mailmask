Decide what happens to mail sent to any address on your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> that isn't one of your aliases.

## Why Use This Feature?

1. Rejecting unknown addresses tells senders the address doesn't exist so guessed addresses get a clear bounce.
2. Dropping unknown addresses gives spammers no signal about which addresses are real.
3. Forwarding unknown addresses lets you make up an address on the spot and still receive the mail.

## Options

Set `unknown_alias_action` in the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology>, or choose it under **Settings** in the `mm` menu.

| Value     | What happens                                               |
|-----------|------------------------------------------------------------|
| `reject`  | The sender gets a bounce saying the address was not found. |
| `drop`    | The message is accepted and silently discarded.            |
| `forward` | The message is forwarded to `default_destination`.         |

```json title="config.json"
{
  "settings": {
    "unknown_alias_action": "forward",
    "default_destination": "personal"
  }
}
```

The <Terminology title="What happens to mail for an address you never made" to="/docs/reference/terminology#aliases-and-mail-flow">unknown alias action</Terminology> applies because the <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> sends every address without its own Email Routing rule to the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>.

## Refusals Never Fall Through

A known <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> that is disabled, expired, or refuses a sender never forwards to the default <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology>. That way, turning off an <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> really stops its mail, even with `forward` selected.

| Setting   | What a refusal does      |
|-----------|--------------------------|
| `reject`  | Bounces with the reason. |
| `drop`    | Discards silently.       |
| `forward` | Bounces with the reason. |

## Other Domains

Mail for any domain other than your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology>, including subdomains of it such as `x@sub.example.com`, is always rejected with `Recipient domain is not handled by this Worker`, whatever your <Terminology title="What happens to mail for an address you never made" to="/docs/reference/terminology#aliases-and-mail-flow">unknown alias action</Terminology> is. It never triggers a notification.

This can happen if you route another domain's catch-all at the same <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>, or if `base_domain` is set to a subdomain while the zone's <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> sends apex mail to the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>.

:::tip
`drop` keeps spammers guessing, but a person who mistypes an address also gets no bounce. It is recommended to pick `reject` unless spam to random addresses is a real problem for you.
:::
