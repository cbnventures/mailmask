Describe your inboxes, aliases, and routing behavior in one `config.json` file that the CLI manages and the deploy command ships to the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>.

## Why Use This File?

1. Keeps every <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology>, <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology>, and setting in one place so a deploy always ships a complete, consistent picture.
2. Is validated against a schema before every deploy so typos and missing references never reach your mail.
3. Is written for you by the CLI so you rarely need to edit JSON by hand, including notifier credentials and service-specific fields.

## File Location

The CLI looks for `config.json` in these locations, in order:

1. The current working directory.
2. The project root, meaning the nearest folder at or above the working directory whose `package.json` declares workspaces (or else the nearest folder with a `package.json`).
3. Your platform config directory (for example `~/.config/mailmask/` on Linux).

If none exists, the CLI copies the bundled starter template into the platform config directory. When several files are found, the interactive menu asks which one to use, while direct commands always use the first one in this order.

The starter template is sample data: a `personal` <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> for `you@example.com`, two aliases that forward to it, one placeholder for every supported notifier type, and a sample `base_domain`. Replace or remove all sample entries, and set `base_domain` to your own apex domain, before the first deploy, as the [Quick Start](/docs/getting-started/quick-start/#first-time-setup) shows.

:::warning
The <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> lists your real inboxes and every <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> you own. It is recommended to keep it out of version control; the repository's ignore rules already exclude it.
:::

## Example

```json title="config.json"
{
  "destinations": [
    {
      "name": "personal",
      "email": "you@example.com"
    }
  ],
  "aliases": [
    {
      "address": "velvet-harbor-42",
      "destination": "personal",
      "label": "Online shopping",
      "enabled": true
    },
    {
      "address": "trial-signup",
      "destination": "personal",
      "label": "Free trial",
      "enabled": true,
      "expires_at": "2026-12-31T00:00:00.000Z",
      "allowed_senders": [
        "*@example-saas.com"
      ]
    }
  ],
  "notifiers": [],
  "settings": {
    "worker_name": "mailmask",
    "base_domain": "example.com",
    "unknown_alias_action": "reject",
    "subaddressing": true,
    "add_alias_headers": true
  }
}
```

## Destinations

Each <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> is a real inbox that aliases forward to.

| Field   | Description                                                                      |
|---------|----------------------------------------------------------------------------------|
| `name`  | Short identifier used by aliases. Lowercase letters, numbers, and hyphens only.  |
| `email` | The inbox address. Cloudflare sends it a verification email on the first deploy. |

## Aliases

Each <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> is an address on your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology>.

| Field             | Description                                                                                        |
|-------------------|----------------------------------------------------------------------------------------------------|
| `address`         | The part before the `@`. Lowercase letters, numbers, dots, hyphens, and underscores, up to 64.     |
| `destination`     | The `name` of the destination to forward to.                                                       |
| `label`           | Optional note about where you used the alias. Added to forwarded mail as `X-Mailmask-Label`.       |
| `enabled`         | `false` refuses all mail while keeping the address reserved.                                       |
| `expires_at`      | Optional ISO 8601 timestamp. Mail arriving at or after this time is refused.                       |
| `allowed_senders` | Optional list of sender rules. When present, only matching senders get through.                    |
| `blocked_senders` | Optional list of sender rules. Matching senders are always refused, even if they are also allowed. |

A <Terminology title="Who an alias will or won't take mail from" to="/docs/reference/terminology#aliases-and-mail-flow">sender rule</Terminology> is either a full address (`news@shop.com`) or a domain wildcard (`*@shop.com`), matched against the envelope sender (`Return-Path`) rather than the visible `From` header. See [Sender Rules](/docs/features/sender-rules/) for how the two lists combine.

## Settings

| Field                  | Description                                                                                        |
|------------------------|----------------------------------------------------------------------------------------------------|
| `worker_name`          | Name of the Cloudflare Worker. Lowercase letters, numbers, and hyphens.                            |
| `base_domain`          | The apex (root) domain of your Cloudflare zone, such as `example.com`. Every alias lives on it.    |
| `unknown_alias_action` | What happens to mail for addresses that are not aliases: `reject`, `drop`, or `forward`.           |
| `default_destination`  | Destination that receives unknown-address mail. Required when `unknown_alias_action` is `forward`. |
| `subaddressing`        | When `true`, `alias+tag@` is treated as `alias@`.                                                  |
| `add_alias_headers`    | When `true`, forwarded mail carries `X-Mailmask-Alias` and `X-Mailmask-Label` headers.             |

The interactive **Settings** menu edits every field.

## Notifiers

The `notifiers` list sends a notice whenever a known alias refuses mail. It is required, but it can be empty (`[]`) when you don't want notices. Every entry needs a unique `name`.

| `type`               | Required fields                                     | Optional fields |
|----------------------|-----------------------------------------------------|-----------------|
| `apprise`            | `name`, `url`                                       | `urls`          |
| `discord`            | `name`, `webhook_url`                               | None            |
| `email`              | `name`, `from`, `to`                                | None            |
| `gotify`             | `name`, `url`, `token`                              | None            |
| `matrix`             | `name`, `homeserver_url`, `room_id`, `access_token` | None            |
| `ntfy`               | `name`, `server`, `topic`, `token`                  | None            |
| `ntfy-reverse-proxy` | `name`, `url`                                       | `token`         |
| `pushover`           | `name`, `user_key`, `app_token`                     | None            |
| `slack`              | `name`, `webhook_url`                               | None            |
| `telegram`           | `name`, `bot_token`, `chat_id`                      | None            |
| `webhook`            | `name`, `url`                                       | `token`         |

All configured URLs must use HTTPS. Discord and Slack webhook URLs must use their service's documented hostname and path prefix. Matrix `room_id` values start with `!`, and ntfy tokens start with `tk_`.

The email notifier's `from` address must use a domain onboarded for Cloudflare Email Sending, and its `to` address must be a verified Cloudflare destination. Deploy creates the `send_email` binding allowlist and registers a new recipient for verification.

See [Refusal Notifications](/docs/features/notifications/) for setup steps, request formats, the exact webhook payload, and service-specific limits.

:::warning
Notifier tokens, webhook URLs, and other credentials are stored in `config.json` and copied to `.wrangler/mailmask/config.json` for bundling into the Worker. Keep both paths out of version control.
:::

## Validation

`mm validate` checks the file against the schema and these cross-references:

- Every <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> points to a <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> that exists.
- No two destinations share a name, and no two aliases share an address.
- No two notifiers share a name.
- `default_destination` exists whenever it is set.

The cross-reference checks only run once the schema check passes, so fixing schema errors can reveal more problems on the next run.

Deploy runs the same validation and stops if the file is invalid, so nothing broken reaches Cloudflare.

## Applying Changes

Alias and setting changes take effect on the next deploy, because the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> ships with the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>. Every CLI command that changes the file reminds you to run `mm deploy`.

:::info
Every CLI save rewrites the whole file: destinations are sorted by name, aliases by address, keys are put in a fixed order, and unknown top-level keys are dropped. Unknown keys inside a <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology>, <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology>, notifier, or the settings fail validation instead.
:::
