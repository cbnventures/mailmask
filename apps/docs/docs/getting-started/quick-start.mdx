Install the CLI, create your first <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology>, and deploy the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> that forwards its mail to your real inbox.

## Prerequisites

- **Node.js** — v22, v24, or v26, with npm.
- **Cloudflare account** — The free plan includes Workers and <Terminology title="Cloudflare's mail intake that hands messages to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">Cloudflare Email Routing</Terminology>.
- **A domain on Cloudflare** — The domain's DNS must be managed by Cloudflare.
- **Email Routing records added** — In the Cloudflare dashboard, open **Email Routing** for the domain, go to **Settings**, and under **DNS records** select **Add missing records** so the mail (MX) records are added. For a subdomain, add it under **Settings > Subdomains** instead.
- **An API token** — With the permission groups listed in [API Token Permissions](/docs/getting-started/deployment#api-token-permissions).

:::warning
The deploy command never adds the Email Routing mail records; it only attaches the base domain and its `www` host to the Worker as custom domains. If <Terminology title="Cloudflare's mail intake that hands messages to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">Cloudflare Email Routing</Terminology> isn't receiving mail for the domain, deploy stops before changing anything and names the dashboard steps to take first.
:::

## Install

Install the package globally to use the `mm` command anywhere:

```bash
npm install -g mailmask
```

Or run it without installing:

```bash
npx mailmask
```

`mailmask` and `mm` are the same command. The first run copies a starter `config.json` into your platform config directory (for example `~/.config/mailmask/` on macOS and Linux), so you don't need to clone the repository.

:::warning
The starter <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> is sample data. Unless you replace it, deploy registers the sample inbox with Cloudflare and publishes the sample aliases on your domain:

- A `personal` <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> that points at `you@example.com`.
- Two sample aliases, `velvet-harbor-42` and `trial-signup`, that forward to `personal`.
- One placeholder for every supported notifier type. They contain example URLs, addresses, and tokens that must not be deployed as-is.
- A sample `base_domain` that has to become your own domain.

Replace or remove the samples and set your own <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> before your first deploy; the steps below show how.
:::

## First-Time Setup

Run `mm` with no arguments to open the interactive menu, then work through these steps.

1. **Open Settings.** Set the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> name and the email domain, which becomes your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> and can be your zone's apex domain, such as `example.com`, or a [subdomain set up in Email Routing](/docs/getting-started/deployment/#cloudflare-requirements).
2. **Remove the sample aliases.** Under **Manage Aliases**, choose **Modify**, pick `velvet-harbor-42`, choose **Remove**, and confirm, then do the same for `trial-signup`.
3. **Replace the sample destination.** Under **Manage Destinations**, remove `personal`, which only works once no <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> uses it, then add it again with your real inbox address.
4. **Remove the sample notifiers.** Set `notifiers` to `[]` in `config.json`, or remove every entry under **Manage Notifiers**; you can [add your own](/docs/features/notifications/#supported-services) at any time.
5. **Create an alias.** Under **Manage Aliases**, choose **Create**, pick an address style, and choose the <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> to forward to.
6. **Deploy.** Choose **Deploy** and paste a Cloudflare <Terminology title="The key that lets the CLI deploy to your account" to="/docs/reference/terminology#cloudflare-and-deploy">API token</Terminology> when asked.

The same steps work as direct commands, except the Settings step, because settings have no direct command. Set `base_domain` in the menu's **Settings** or in `config.json` first, then run:

```bash
# Remove the sample aliases, then swap the sample inbox for your real one.
mm alias remove velvet-harbor-42
mm alias remove trial-signup
mm destination remove personal
mm destination add personal you@example.com

# Remove the sample notifiers.
mm notifier remove apprise
mm notifier remove discord
mm notifier remove email
mm notifier remove gotify
mm notifier remove matrix
mm notifier remove phone
mm notifier remove reverse-proxy
mm notifier remove pushover
mm notifier remove slack
mm notifier remove telegram
mm notifier remove webhook

# Create a memorable alias that forwards to your inbox.
mm alias add -d personal -l "Online shopping"

# Give deploy your Cloudflare API token.
export CLOUDFLARE_API_TOKEN=your-token

# Validate, register the inbox, deploy, and add a routing rule for each alias.
mm deploy
```

Use your real inbox in place of `you@example.com`. A direct `mm deploy` never prompts for a token, so it reads `CLOUDFLARE_API_TOKEN` from the environment or from the `.env` file in your config directory, as [Providing the Token](/docs/getting-started/deployment/#providing-the-token) explains.

## Verify Your Inbox

On the first deploy, Cloudflare sends a verification email to each new <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology>. Mail for an <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> can't reach that inbox until you click the link in that email.

:::tip
Run `mm deploy` again after verifying. The summary confirms that every <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> is verified and lists each <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> with its full address.
:::

## Send a Test Message

Send an email from any account to the address the CLI printed, such as `velvet-harbor-42@example.com`. It arrives in your real inbox within a few seconds.

When alias headers are enabled, the forwarded message carries `X-Mailmask-Alias` and `X-Mailmask-Label` headers. You can use them to build filters in your mail client.

## If Something Goes Wrong

Check [Troubleshooting](/docs/reference/troubleshooting/) for the most common first-run problems:

- Email Routing not receiving mail for the domain.
- A <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> that has not been verified yet.
- An <Terminology title="The key that lets the CLI deploy to your account" to="/docs/reference/terminology#cloudflare-and-deploy">API token</Terminology> missing one of the required permission groups.
