Publish your aliases to Cloudflare with a single `mm deploy` that handles the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>, your inboxes, and the <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> for you.

## Cloudflare Requirements

- **Cloudflare account** — Free or paid.
- **A domain managed by Cloudflare DNS** — The <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> should be the zone's apex (root) domain, such as `example.com`, rather than a subdomain.
- **Email Routing enabled** — Enable it once under **Email > Email Routing** so Cloudflare adds the MX and SPF records.
- **Email Sending configured when using an email notifier** — Onboard the notifier's sender domain in Cloudflare Email Sending. Other notifier types do not need this service.
- **An API token** — With the three permissions listed below.

:::info
Enabling Email Routing changes your DNS, so Mailmask leaves that step to you. If it isn't enabled, deploy stops with a message pointing to the dashboard.
:::

:::warning
Cloudflare only offers catch-all rules on the apex domain, and a subdomain has to be added on its own under **Email Routing > Settings > Subdomains** ([Cloudflare docs](https://developers.cloudflare.com/email-service/configuration/subdomains/)). Deploy relies on the zone's <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> rule, so a subdomain <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> doesn't receive mail.
:::

## API Token Permissions

Create a custom token at [dash.cloudflare.com/profile/api-tokens](https://dash.cloudflare.com/profile/api-tokens) with these permissions.

| Permission                               | Why it is needed                                              |
|------------------------------------------|---------------------------------------------------------------|
| Account > Workers Scripts > Edit         | Publishes the Worker.                                         |
| Account > Email Routing Addresses > Edit | Registers each destination inbox and checks its verification. |
| Zone > Email Routing Rules > Edit        | Points the zone's catch-all rule at the Worker.               |

Under **Account Resources**, select your account. Under **Zone Resources**, select the zone that holds your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology>.

## Providing the Token

- **Interactive deploy** — Choosing **Deploy** in the `mm` menu walks you through creating a token, verifies it, and saves it as `CLOUDFLARE_API_TOKEN` in a `.env` file in your config directory.
- **Direct command** — `mm deploy` reads `CLOUDFLARE_API_TOKEN` from the environment or that `.env` file. It stops with an error instead of prompting when no valid token is found.

At startup, the CLI loads only the first `.env` file it finds, checking the working directory, then the project root, then the config directory. If that file has no token, deploy still falls back to the `.env` in your config directory.

If the token has no access to one of these resources, deploy lists exactly which permissions to add. In the interactive menu, it waits while you update the token and then retries.

:::warning
The permission check only confirms the token can reach each resource, so it can't tell **Read** access from **Edit**. A token with **Read** passes the check and then fails partway through deploy with a Cloudflare API error, so it is recommended to set all three permissions to **Edit**.
:::

## What Deploy Does

1. **Authenticates** — Confirms the <Terminology title="The key that lets the CLI deploy to your account" to="/docs/reference/terminology#cloudflare-and-deploy">API token</Terminology> is valid.
2. **Validates** — Checks the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> and stops if anything is wrong.
3. **Finds the zone** — Locates the Cloudflare zone for your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> and verifies the token's permissions.
4. **Checks Email Routing** — Confirms <Terminology title="Cloudflare's mail intake that hands messages to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">Cloudflare Email Routing</Terminology> is enabled on the zone.
5. **Registers destinations** — Adds any new forwarding destination or email-notifier recipient to Email Routing, which triggers a verification email, and lists the ones still unverified.
6. **Generates `wrangler.toml`** — Writes the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> configuration next to your `config.json`, plus `.wrangler/mailmask/config.json` beside it with your whole config, notifier tokens included, which ships inside the Worker. When email notifiers exist, it also generates the `MAILMASK_EMAIL` `send_email` binding and its recipient allowlist. It is recommended to keep `.wrangler/` out of version control.
7. **Publishes the Worker** — Runs `wrangler deploy`.
8. **Points the catch-all** — Sets the zone's <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> rule to send mail to the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>, unless it already does.
9. **Prints a summary** — Lists every <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> with its full address, <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology>, and status.

:::warning
Pointing the <Terminology title="Sends every address to Mailmask, so new aliases just work" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> at the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> replaces whatever the catch-all did before, and deploy prints the previous action. Explicit Email Routing rules for individual addresses still take precedence over the catch-all.
:::

## Verifying Destinations

Cloudflare only forwards or sends to verified destination inboxes. Until you click the link in the verification email, mail for any <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> that uses that <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> can't be delivered, and an email notifier cannot send to that recipient.

Run `mm deploy` again after verifying to confirm the warning is gone.

## Updating Aliases

Every change to the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> reaches Cloudflare on the next deploy. A typical retire-and-redeploy looks like this:

```bash
# Stop accepting mail at an address that started getting spam.
mm alias disable velvet-harbor-42

# Ship the change.
mm deploy
```

## Worker Exposure

The generated configuration turns off the `workers.dev` address and preview URLs. The <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> shows its service page at the root, returns a JSON `404` error for other `GET` and `HEAD` paths, and returns a JSON `405` error for unsupported methods.
