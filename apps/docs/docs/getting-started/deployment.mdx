Publish your aliases to Cloudflare with a single `mm deploy` that handles the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>, your inboxes, and a <Terminology title="Sends one alias's mail to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">routing rule</Terminology> for every enabled alias.

## Cloudflare Requirements

- **Cloudflare account** — Free or paid.
- **A domain managed by Cloudflare DNS** — The <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> can be the zone's apex (root) domain, such as `example.com`, or a subdomain, such as `mail.example.com`.
- **Email Routing receiving mail for the base domain** — For an apex, open **Email Routing** for the domain, go to **Settings**, and under **DNS records** select **Add missing records** so Cloudflare adds the MX and SPF records. For a subdomain, add it under **Email Routing > Settings > Subdomains** so Cloudflare adds its records ([Cloudflare docs](https://developers.cloudflare.com/email-service/configuration/subdomains/)).
- **Email Sending configured when using an email notifier** — Onboard the notifier's sender domain in Cloudflare Email Sending. Other notifier types do not need this service. With `send_from_aliases` on, deploy onboards the base domain for you.
- **An API token** — With the permissions listed below.

:::info
Adding Email Routing records changes your DNS, so Mailmask leaves that step to you. If the base domain isn't set up, deploy stops before changing anything, with a message that names the dashboard steps. The only DNS records deploy adds are the Email Sending ones, and only with `send_from_aliases` on.
:::

## API Token Permissions

Create a token at [dash.cloudflare.com/profile/api-tokens](https://dash.cloudflare.com/profile/api-tokens) with **Create Token**, then start from scratch with a custom token.

Under **Account policy**, select your account; under **Zone policy**, select the zone that holds your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology>. In each policy, search for the permission group by name and tick **Read** or **Edit** as listed.

| Permission                               | Why it is needed                                                                          |
|------------------------------------------|-------------------------------------------------------------------------------------------|
| Account > Workers Scripts > Edit         | Publishes the Worker and lists and attaches its custom domains.                           |
| Account > Email Routing Addresses > Edit | Registers each destination inbox and checks its verification.                             |
| Zone > Zone Settings > Edit              | Reads the Email Routing status and turns on subaddressing when `subaddressing` is `true`. |
| Zone > Email Routing Rules > Edit        | Adds, updates, and removes alias routing rules and turns off a catch-all for the Worker.  |
| Zone > Workers Routes > Edit             | Attaches the base domain and its `www` host to the Worker as custom domains.              |
| Zone > Email Sending > Edit              | Only with `send_from_aliases` on: onboards the base domain to Cloudflare Email Sending.   |
| Zone > DNS > Edit                        | Only with `send_from_aliases` on: adds the DNS records Email Sending needs.               |
| Account > Billing > Read                 | Only with `send_from_aliases` on: reads whether the account is on Workers Paid.           |

## Providing the Token

- **Interactive deploy** — Choosing **Deploy** in the `mm` menu walks you through creating a token, verifies it, and saves it as `CLOUDFLARE_API_TOKEN` in a `.env` file in your config directory.
- **Direct command** — `mm deploy` reads `CLOUDFLARE_API_TOKEN` from the environment or that `.env` file. It stops with an error instead of prompting when no valid token is found.

At startup, the CLI loads only the first `.env` file it finds, checking the working directory, then the project root, then the config directory. If that file has no token, deploy still falls back to the `.env` in your config directory.

Before anything changes, deploy reads every Cloudflare endpoint it uses and lists exactly which permission groups to add, such as `Zone > Zone Settings > Edit`. In the interactive menu, it waits while you update the token and then retries.

:::warning
The permission check only confirms the token can read each resource, so it can't tell **Read** access from **Edit**. A token with **Read** passes the check and then fails partway through deploy with a Cloudflare API error, so it is recommended to tick **Edit** for every row above.
:::

## What Deploy Does

1. **Authenticates** — Confirms the <Terminology title="The key that lets the CLI deploy to your account" to="/docs/reference/terminology#cloudflare-and-deploy">API token</Terminology> is valid.
2. **Validates** — Checks the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> and stops if anything is wrong.
3. **Finds the zone** — Locates the Cloudflare zone for your <Terminology title="The domain every alias lives on" to="/docs/reference/terminology#cloudflare-and-deploy">base domain</Terminology> and verifies the token's permissions.
4. **Checks Email Routing** — Confirms <Terminology title="Cloudflare's mail intake that hands messages to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">Cloudflare Email Routing</Terminology> is enabled on an apex, or that a subdomain's MX records point to Cloudflare.
5. **Plans the changes** — Lists the zone's <Terminology title="Your Worker's own web addresses" to="/docs/reference/terminology#cloudflare-and-deploy">custom domains</Terminology> and <Terminology title="Sends one alias's mail to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">routing rules</Terminology>, and stops before any change when a host belongs to another Worker or the domain would pass Cloudflare's rule limit.
6. **Registers destinations** — Adds any new forwarding destination or email-notifier recipient to Email Routing, which triggers a verification email, and lists the ones still unverified.
7. **Generates `wrangler.toml`** — Writes the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> configuration next to your `config.json`, plus `.wrangler/mailmask/config.json` beside it with your whole config, notifier tokens included, which ships inside the Worker. When email notifiers exist, it also generates the `MAILMASK_EMAIL` `send_email` binding and its recipient allowlist. With `send_from_aliases` on, the binding is always generated and has no allowlist, so replies can reach any recipient. It is recommended to keep `.wrangler/` out of version control.
8. **Publishes the Worker** — Runs `wrangler deploy`.
9. **Attaches custom domains** — Adds the base domain and `www.` plus the base domain as <Terminology title="Your Worker's own web addresses" to="/docs/reference/terminology#cloudflare-and-deploy">custom domains</Terminology> of the Worker, unless they already are.
10. **Turns on subaddressing** — When `subaddressing` or `send_from_aliases` is `true`, turns on Email Routing subaddressing so `alias+tag@` and reply addresses match the alias's rule. It never turns the setting off.
11. **Syncs routing rules** — Adds a <Terminology title="Sends one alias's mail to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">routing rule</Terminology> for each enabled <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology>, fixes rules that changed, and removes the ones for disabled or removed aliases.
12. **Hands back the catch-all** — Turns off any <Terminology title="Cloudflare's rule for addresses without their own rule" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> that points at the Worker, such as the one Mailmask 1.0.0 set up, once every enabled alias has its own rule.
13. **Sets up Email Sending** — When `send_from_aliases` is on, onboards the base domain to Cloudflare Email Sending unless it already is, then adds each DNS record Email Sending expects that the zone lacks. An existing DMARC record is kept. If Cloudflare refuses, deploy warns and carries on, because mail still forwards. It then waits up to a minute for those records to resolve on public DNS, and reads the account's Workers plan.
14. **Connects phone numbers** — When the config has phone aliases, points each <Terminology title="The Telnyx or Plivo account that rents your numbers" to="/docs/reference/terminology#phone-aliases">phone provider</Terminology>'s numbers at `https://<base_domain>/phone/<provider>/messages`, as [Phone Providers](/docs/getting-started/phone-providers/) describes.
15. **Prints a summary** — Lists every <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> and <Terminology title="A rented number that forwards its texts to you" to="/docs/reference/terminology#phone-aliases">phone alias</Terminology> with its <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> and status, then warns about the caveats that apply: **Reply All** when `send_from_aliases` is on, Email Sending records that are still pending, Workers Paid when the account is on Workers Free or its plan can't be read, caller ID when there are phone aliases, and console-only country limits when there is a Plivo account.

Running deploy again changes only what differs in destinations, custom domains, routing rules, and Email Sending setup, so a redeploy with no config changes adds, updates, and removes none of them. It still regenerates `wrangler.toml` and publishes the Worker on every run.

## Routing Rules

Deploy keeps one literal Email Routing rule per enabled <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology>, such as `shop@example.com`, that sends its mail to the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>. Each rule's name starts with `mailmask:` and the Worker name, which is how deploy tells its own rules apart.

- **Rules you or another Worker created** — Deploy never changes or removes them. If one already handles an alias's address, deploy leaves it in place and prints a warning instead of adding a second rule.
- **Several Workers on one zone** — Each Mailmask Worker manages only its own rules, so `mailmask` on `example.com` and `mailmask-dev` on `dev.example.com` can share a zone.
- **Rule limit** — Cloudflare allows 200 routing rules per domain ([Cloudflare docs](https://developers.cloudflare.com/email-routing/limits/)). Deploy counts every rule on the base domain, including ones it didn't create, and stops before passing that limit.
- **Disabled aliases** — A disabled alias has no rule, so its mail is rejected like an unknown address and doesn't notify.

:::info
Mail to an address without a rule never reaches the Worker. Cloudflare rejects it with `Address does not exist`, and the sender's server does not retry ([Cloudflare docs](https://developers.cloudflare.com/email-service/configuration/domains/)).
:::

## Upgrading From 1.0.0

Mailmask 1.0.0 pointed the zone's <Terminology title="Cloudflare's rule for addresses without their own rule" to="/docs/reference/terminology#cloudflare-and-deploy">catch-all</Terminology> at the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology>. The first deploy after upgrading adds a <Terminology title="Sends one alias's mail to Mailmask" to="/docs/reference/terminology#cloudflare-and-deploy">routing rule</Terminology> for each enabled alias first, then turns off any catch-all that points at this Worker and says so in its output.

- **Catch-all pointing elsewhere** — Deploy leaves a catch-all that forwards, drops, or points at a different Worker untouched.
- **Previous catch-all action** — Mailmask 1.0.0 didn't store the action it replaced, so deploy turns the catch-all off rather than guessing what to restore.
- **Old settings** — A config that still has `unknown_alias_action` or `default_destination` keeps working. The CLI prints a one-line notice, ignores both, and leaves them out on its next save.

## Verifying Destinations

Cloudflare only forwards or sends to verified destination inboxes. Until you click the link in the verification email, mail for any <Terminology title="A stand-in address; mail still lands in your real inbox" to="/docs/reference/terminology#aliases-and-mail-flow">alias</Terminology> that uses that <Terminology title="Your real inbox, where an alias's mail ends up" to="/docs/reference/terminology#aliases-and-mail-flow">destination</Terminology> can't be delivered, and an email notifier cannot send to that recipient.

Run `mm deploy` again after verifying to confirm the warning is gone.

## Updating Aliases

Every change to the <Terminology title="The one file that holds every alias and setting" to="/docs/reference/terminology#cloudflare-and-deploy">config</Terminology> reaches Cloudflare on the next deploy. A typical retire-and-redeploy looks like this:

```bash
# Stop accepting mail at an address that started getting spam.
mm alias disable velvet-harbor-42

# Ship the change, which removes the alias's routing rule.
mm deploy
```

## Worker Exposure

The generated configuration turns off the `workers.dev` address and preview URLs, so the <Terminology title="Mailmask itself, running on your Cloudflare account" to="/docs/reference/terminology#cloudflare-and-deploy">Worker</Terminology> answers web requests only on its <Terminology title="Your Worker's own web addresses" to="/docs/reference/terminology#cloudflare-and-deploy">custom domains</Terminology>.

- **Base domain** — Shows the service page at the root, returns a JSON `404` error for other `GET` and `HEAD` paths, and returns a JSON `405` error for unsupported methods.
- **`www` host** — Redirects every request to the base domain with a `301`, keeping the path and query string.
- **Host already in use** — Deploy stops before any change when another Worker owns either host, and never moves or removes a custom domain it didn't create. If Cloudflare refuses a host because it already has its own DNS records, such as a website's `A` record or a `CNAME`, deploy warns and carries on, and mail still works.
